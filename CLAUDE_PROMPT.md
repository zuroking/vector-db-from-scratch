# PROJECT PROMPT: `vector-db-from-scratch`

## Роль

Ты выступаешь в роли senior Python/ML-инженера, реализующего production-grade собственную векторную базу данных с нуля. Архитектурные решения принимает пользователь (архитектор/ревьюер), ты — implementation agent. **Не начинай писать код, пока раздел "Открытые архитектурные решения" не закрыт явным ответом пользователя.**

---

## 1. Цель проекта

Реализовать самодостаточную векторную базу данных на Python без использования FAISS, Chroma, Annoy, hnswlib или любых сторонних ANN-библиотек. Единственная разрешённая численная зависимость — `numpy`. Проект — часть портфолио, приоритет: глубина понимания алгоритмов > production-полнота.

---

## 2. Технический стек (жёстко зафиксировано)

| Параметр | Значение |
|---|---|
| Python | 3.12+ |
| Валидация данных | Pydantic v2 (строгие модели для всех публичных структур) |
| Типизация | strict mypy, `disallow_untyped_defs = true`, без `Any` без обоснования |
| Численные вычисления | только `numpy` |
| Векторные индексы | HNSW **или** IVF (выбор фиксируется до старта кодинга — см. раздел 4) |
| Тесты | `pytest`, обязательное покрытие edge-cases (пустой индекс, дубликаты векторов, размерность-мисматч) |
| Docstrings | Google-style, на английском (код — на английском, комментарии по решениям — можно на русском) |
| CLI (опционально, Phase 5) | Typer + Rich |

Запрещено: FAISS, Chroma, hnswlib, Annoy, ScaNN, любые готовые ANN/векторные библиотеки.

---

## 3. Функциональные требования

- Метрики расстояния: **Cosine similarity** и **L2 (Euclidean)**, переключаемые на уровне индекса через enum, без дублирования кода расчёта (вынести в отдельный модуль `distances.py` с векторизованными numpy-реализациями).
- CRUD операций: `insert`, `delete` (soft или hard — см. открытые решения), `search(query, k, metric)`.
- Персистентность на диск: сериализация индекса и метаданных в бинарный/структурированный формат с возможностью полного восстановления состояния (загрузка без пересчёта индекса с нуля).
- Метаданные векторов (id, произвольный payload) хранятся и возвращаются вместе с результатами поиска.

## 4. Открытые архитектурные решения (ЗАБЛОКИРОВАТЬ ПЕРЕД КОДОМ)

Claude Code должен задать пользователю следующие вопросы явным списком в первом ответе, **до генерации какого-либо кода**:

1. **HNSW vs IVF** — какой индекс реализуем? (Компромиссы: HNSW — лучше recall/latency, сложнее в реализации графа и multi-layer навигации; IVF — проще, но требует этапа обучения кластеров (k-means) и хуже recall на малых `nprobe`.)
2. **Thread-safety** — нужна ли потокобезопасность на запись (insert/delete во время поиска)? Если да — какой механизм (RWLock, копирование-на-запись, single-writer)?
3. **Формат персистентности** — сырой pickle/numpy `.npy` + JSON-метаданные, или кастомный бинарный формат с версионированием схемы?
4. **Удаление векторов** — soft-delete (tombstone-флаг, без перестройки графа/кластеров) или hard-delete (полная перестройка структуры)?
5. **Размерность векторов** — фиксируется при создании индекса (строгая валидация Pydantic) или допускается динамическое изменение?
6. **Distance metric при построении индекса** — фиксируется на уровне индекса (один индекс = одна метрика) или допускается multi-metric поиск по одному индексу?

## 5. Фазы реализации

### Phase 0 — Скелет проекта
- Структура директорий (`src/vectordb/{core,index,distances,persistence,cli}`), `pyproject.toml`, `mypy.ini`/`pyproject` strict-конфиг, `pytest` setup.
- Базовые Pydantic-модели: `VectorRecord`, `SearchResult`, `IndexConfig`.
- **Не переходить к Phase 1 без подтверждения пользователем структуры.**

### Phase 1 — Модуль расстояний (`distances.py`)
- Векторизованные numpy-реализации cosine и L2.
- Unit-тесты: известные аналитические случаи (ортогональные векторы, идентичные векторы, нулевой вектор — обработка деления на ноль в cosine).

### Phase 2 — Индексная структура (ядро)
- Реализация выбранного индекса (HNSW: layered graph + greedy search + `ef_construction`/`ef_search`; или IVF: k-means кластеризация + inverted lists + `nprobe`).
- Явно документировать сложность операций (insert/search) в docstring.

### Phase 3 — Поиск и ранжирование
- `search(query, k, metric) -> list[SearchResult]`, отсортированный по релевантности.
- Обработка edge cases: `k > len(index)`, пустой индекс, query размерность не совпадает с индексом (должен кидать типизированное исключение, не падать безмолвно).

### Phase 4 — Персистентность
- `save(path)` / `load(path)` — полное round-trip сохранение состояния индекса без потери recall-качества.
- Тест: построить индекс → сохранить → загрузить в новый процесс/объект → сравнить результаты поиска на одинаковых запросах (bit-for-bit или в пределах допустимой погрешности).

### Phase 5 — CLI и бенчмарки (опционально)
- Typer CLI: `insert`, `search`, `build-index`, `benchmark`.
- Бенчмарк recall@k и latency против brute-force (numpy linear scan) baseline на синтетическом датасете.

### Phase 6 — Тестовое покрытие и финальный аудит
- Полный прогон pytest с coverage-отчётом.
- Финальный вывод: список принятых архитектурных допущений, известных ограничений, потенциальных векторов для будущей оптимизации (например, quantization, product quantization, disk-based ANN для больших датасетов).
